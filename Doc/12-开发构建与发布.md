## 2. 首次开发

```sh
git clone https://github.com/hzxslzb/ComicReader.git
cd ComicReader
java -version
./gradlew --version
```

使用 JDK 17；在 Android Studio 中安装 Android SDK Platform 35 及构建所需组件。SDK 路径通过已有 `ANDROID_HOME` 环境变量或本地 `local.properties` 的 `sdk.dir` 配置。`local.properties` 不提交，因为它包含开发机路径。

首次 Gradle 同步需要联网下载依赖。仓库没有依赖远程业务后端；运行在线搜索／阅读仍需要能访问数据源和图片服务器的网络。Windows 使用 `gradlew.bat` 执行等价任务。

## 3. 开发构建与安装

```sh
./gradlew :app:assembleDebug
./gradlew :app:testDebugUnitTest :app:lintDebug
```

产物：`app/build/outputs/apk/debug/app-debug.apk`。连接专用测试设备后可运行：

```sh
adb devices
./gradlew :app:installDebug
```

Debug 与正式版可共存，不共享收藏、历史和下载。开发中看不到正式版的书架属于正常隔离，不能通过改 Debug 包名去直接操作用户正式库。

## 4. 签名配置

模板：[signing.properties.example](../signing.properties.example)。复制为未跟踪的 `signing.properties`，填写自己的 keystore 路径、storePassword、keyAlias、keyPassword。不要把真实密码放进 README、命令记录或公开日志。

如果是首次自行发行，可以在本地生成自己的密钥，以下命令交互式询问密码：

```sh
mkdir -p signing
keytool -genkeypair -keystore signing/your-release.jks \
  -alias comicreader -keyalg RSA -keysize 3072 -validity 10000
```

**已有官方发行的维护者必须继续使用原密钥，不要用新生成密钥替换。** 自行签名包不能覆盖官方签名安装；自己的后续版本也要保留同一密钥。签名文件、真实配置和恢复材料需要在仓库之外安全备份。

[.gitignore](../.gitignore) 已排除 signing/、signing.properties、常见 keystore 扩展名、local.properties、构建目录和 APK/AAB。忽略规则不会自动移除已经被跟踪的文件，发布前仍要检查暂存区。

## 5. Release 构建与产物核验

完成签名配置后：

```sh
./gradlew :app:assembleRelease
```

签名 APK 位于 `app/build/outputs/apk/release/`，通常为 `app-release.apk`。当前 release 未启用代码混淆；不要文档先声称已完成 R8 优化。

使用安装在 Android SDK build-tools 中的 apksigner 校验，工具在 PATH 时可以执行：

```sh
apksigner verify --verbose --print-certs app/build/outputs/apk/release/app-release.apk
```

核对包名、versionName、versionCode 和证书摘要，再在保留旧数据的测试应用上覆盖安装。当前官方签名证书 SHA-256 为：

```text
5727eb7043ded618c77075aefa8006c52eea470f89d30bb77b5a7a80d162aa95
```

证书摘要是公开身份标识，不是签名私钥。仅 APK 文件哈希相同／不同不能代替证书核验。构建代码或资源变化后 APK 哈希会变化，而证书应保持稳定。

## 6. 数据兼容性检查

正式更新需要同时保持包名和签名，并递增 versionCode。本版数据库仍为 version 1，私有目录仍为 `files/chapters`。未来改 schema 时必须实现迁移；当前 `onUpgrade` 并没有通用迁移能力。

覆盖升级测试应准备：至少两本书的独立断点、收藏、完整下载、暂停任务、非默认主题与预加载设置。安装前记录期望值，安装新 APK 后核对逻辑数据和实际离线图片。不要先卸载再测试“升级保留”。

已执行过的历史升级路径见 [TESTING.md](../TESTING.md)，不能将一个已验证路径推广为所有未来版本都已验证。

## 7. GitHub 发布流程

仓库：[hzxslzb/ComicReader](https://github.com/hzxslzb/ComicReader)。目前没有仓库内自动构建发布 workflow；发布由维护者本地构建和 GitHub CLI 完成。

推荐顺序：

1. 实现改动并完成相应验证。
2. 更新 app/build.gradle 的 versionName/versionCode；不要复用已发布版本号替换不同代码。
3. 更新根 README、CHANGELOG、TESTING 及对应 `docs/releases/vX.Y.Z.md`，同步 Doc 中受影响的行为。
4. 确认签名、覆盖升级、权限和离线数据。
5. 提交源码与文档，创建版本 tag，推送对应 commit 和 tag。
6. 为该 tag 生成 APK、源码归档、SHA-256 清单，创建 Release 并上传。
7. 从 Release 页面复核版本、公告、附件名、下载可用性及哈希。

在维护者已经登录 gh、准备好文件、核对版本后，可使用这样的命令模板；将版本变量改为**本次实际新版本**，不要原样重复发布已有 tag：

```sh
release_version='X.Y.Z'
release_tag="v${release_version}"
git status --short
git tag -a "$release_tag" -m "ComicReader $release_tag"
git push origin main
git push origin "$release_tag"
mkdir -p dist
cp app/build/outputs/apk/release/app-release.apk "dist/ComicReader-${release_version}.apk"
git archive --format=zip --prefix=ComicReader/ \
  --output="dist/ComicReader-${release_version}-source.zip" "$release_tag"
(cd dist && shasum -a 256 "ComicReader-${release_version}.apk" \
  "ComicReader-${release_version}-source.zip" > SHA256SUMS.txt)
gh release create "$release_tag" \
  --title "ComicReader $release_tag" \
  --notes-file "docs/releases/${release_tag}.md" \
  "dist/ComicReader-${release_version}.apk" \
  "dist/ComicReader-${release_version}-source.zip" dist/SHA256SUMS.txt
```

上述示例不包含自动 git commit；应先审查并提交。`git archive` 只归档 tag 中的跟踪文件，避免把本地签名文件和缓存打进源码包；前提是这些敏感文件从未被错误提交。dist 中的源码 ZIP 和校验文件也不要误加到源码提交。

## 8. Release 公告内容

公告应说明：新增行为、修复的具体问题、更新安装方式、数据兼容、真实测试范围、已知限制。涉及流量的预加载设置要给出默认值；涉及阅读记录时说明精度；涉及折叠屏时区分模拟器与实体设备。

历史公告对应其发布产物，原则上保留原始版本语义。新增技术文档不需要重新打一个相同版本 APK，也不应为了文档更新虚构代码修复公告。

## 9. 发布失败与回退

- 构建失败：先区分 JDK、SDK、依赖下载、编译、签名配置，不要用删除用户数据库来解决构建问题。
- 签名不匹配：核对 keystore 与已安装包身份，不建议用户卸载以“强制升级”。
- 上传失败：先用 `gh release view` 检查已有 Release 和附件，避免创建重复版本。
- 代码回退：回退提交不等于 Android 可以降级覆盖；versionCode 与数据兼容要另行评估。
- 错误产物已发布：保留清晰记录，修正后以新版本发布。不要静默替换版本号相同但内容不同的安装包。

## 10. 仅文档改动

例如仅补全文档时：执行文档校验、链接核对和差异检查，提交并推送源码仓库即可。没有改应用行为、数据库、签名或 APK，不需要为了文档重复运行全部联网设备测试。文档测试结果与历史应用测试结果应分开报告。
